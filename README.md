# Garden Bistro replacement — work in progress

The official application is `garden-bistro/vite-app` (Vite/React/TypeScript). The root `netlify.toml` builds it from that directory, publishes `dist`, and includes Netlify Functions and an SPA fallback. The old Next.js app is preserved in `garden-bistro/legacy-next` for migration and rollback, not active deployment. The app remains noindex. Do not cut over the production site until migration and end-to-end verification are complete; the actual live deployment has not been inspected.

## Setup

From the repository root, run `cd garden-bistro/vite-app`, then `npm ci` and `npm run dev` for the client. To exercise functions, run through Netlify's function runtime, not the standalone Vite dev server. `npm run typecheck`, `npm test`, and `npm run build` check the client and function TypeScript and run the local tests. The build does not itself exercise Netlify function packaging or deployed services. For local Netlify smoke tests, start an isolated unconfigured Netlify dev server and run `SMOKE_BASE_URL=http://localhost:8888 npm run test:netlify`; the smoke test checks SPA routes, function routing, disabled ordering and rejected requests, not live integrations. In restricted environments, Netlify CLI may require `--internal-disable-edge-functions` to avoid its Edge runtime download.

Client build variables (public; `.env.example`): `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. These must never contain a service-role key. Set them in the Vite build environment. Public content is served via the read-only `public-content` Netlify Function, which returns an allowlisted projection of published records; it uses server-side PostgreSQL credentials rather than direct browser queries. The function requires the proposed `gb_media` table, even if no images are linked. Missing configuration results in unavailable content. Review both the query and all deployed grants and RLS policies independently.

Server-only Netlify variables: `SITE_URL` (exact allowed staging origin, e.g. `https://staging.example.org`), `DATABASE_URL` (server-only PostgreSQL connection), `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (required for staff invitations only), `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, and `R2_PUBLIC_BASE_URL` (HTTPS base URL for **public** images), and `ORDERING_APPROVED` (defaults off; do not set to true without explicit owner approval and full end-to-end testing). Do not prefix any server secret with `VITE_`. Configure Supabase Auth redirect allowlists and email delivery for the staging origin. These functions fail closed when required configuration is missing. The database role requires narrowly scoped permissions for the legacy `content`, `settings`, `orders`, `order_items`, `order_status_history`, `requests`, `rate_limits`, `audit_logs` tables and proposed `gb_staff_access` and `gb_media` tables; grant only what is needed. Confirm IP-header behavior and connection security with the deployment provider.

## Implemented in code

- EN/FR/SW page shells, actual provided imagery and unchanged logo, exact map, database-backed menu/room listings, explicit empty/error states, and disabled ordering.
- Table, hotel and event request forms and Netlify request function with source validation, honeypot, DB-backed rate limit and idempotency. Requests remain pending; no availability is guaranteed. A server-side order submission foundation rechecks prices, availability and settings in a transaction, captures snapshots and uses idempotency; it is disabled unless an additional `ORDERING_APPROVED=true` server switch and business settings are enabled. A localized cart, delivery-zone selector and staff order queue are implemented; prices and delivery fees are rechecked against the customer-confirmed values. There is no payment integration, and the order flow has not been tested with a live database.
- Supabase session restoration, login, logout, reset-email and password-update UI; permission-aware staff sections for request handling, orders, ordering settings and content create/edit; each function checks the permission independently and records changes in the audit log. Staff with both the `owner` role and `staff.manage` can invite and manage non-owner accounts. An invited account only gains access after its mapping is saved; if provisioning fails after an invitation is sent, the resulting account has no staff access and needs operator review. Owners cannot change their own access or other owners through these functions. The request queue has pagination, filtering, stale-update protection and a Realtime subscription that refreshes the queue after request inserts/updates. Realtime depends on the proposed RLS and publication migrations and is unverified on a live Supabase project.
- Menu title/description search, category filtering and unavailable badges based on existing published content data, plus explicit R2 image linking for menu items. Published FAQ and approved about/legal text are displayed when available.
- Authenticated, explicitly permission-checked public R2 image upload with image decoding/format checks, resizing and WebP conversion, randomized keys, download-and-hash verification, DB metadata and audit. A media library can list uploads and edit descriptions with separate read/write permissions. The R2 public domain must be intentionally configured for public objects. Failed metadata writes before commit trigger best-effort deletion; an uncertain commit leaves the object in place and logs its key for reconciliation. Any logged orphan key requires operator review.

## Important gaps and migration status

This is not production-ready. Auth, forms, permissions, Netlify packaging, R2 and live database integration have not been tested against configured services. `migrations/001_staff_access_PROPOSED.sql`, `002_media_PROPOSED.sql`, `003_request_read_rls_PROPOSED.sql` and `004_realtime_requests_PROPOSED.sql`, and `005_legacy_media_map_PROPOSED.sql` are proposals and **have not been applied**; first review the actual deployed schema, grants and RLS policies. A trusted operator must onboard staff through Supabase Auth and separately provision exact permission strings (currently `requests.read`, `requests.write`, `orders.read`, `orders.write`, `settings.read`, `settings.write`, `dashboard.read`, `audit.read`, `media.read`, `media.write`, `staff.manage`, and `content.<kind>.read` / `content.<kind>.write` for the supported content kinds) in `gb_staff_access`; no client can alter its own role. No existing staff hashes have been imported. The old app and new access table are not automatically synchronized.

The full granular RLS model, media replacement/deletion, migration and verification of old PostgreSQL images, most structured content metadata editing, menu image migration, complete admin modules, realtime for orders and other modules, push, localization of staff UI, SEO controls and full ordering preservation are not implemented. Existing static photographs are still bundled rather than migrated to R2. No live records or media have been migrated or counted. Existing published content query access depends on safely configured RLS, not on an assumption that every authenticated user is an admin. Never apply these proposal migrations or cut over without checking compatibility, backups, owner decisions, permissions and end-to-end behavior.

The content editor changes only basic content fields and deliberately retains existing JSON metadata on updates; it can update menu category, sold-out flags and a linked uploaded R2 image without replacing other metadata, but does not yet edit general business-profile settings or other richer fields. A separate ordering-settings form can edit ordering settings; stale edits are rejected. It creates new entries with empty metadata. The public endpoint only returns selected public fields from published records, but the server database role can access private records: review that role, function query and existing RLS policies before deployment. A permissive legacy RLS policy may grant more access than the new proposed request policy because PostgreSQL combines permissive policies with OR. The request realtime migration does not remove such policies. Realtime subscriptions are for INSERT and UPDATE only; delete events are not subscribed. Staff identity and role checks require live Supabase and PostgreSQL and have not been integration-tested. Invites require correct Auth email and redirect setup. The dashboard is currently English-only.

## Legacy media copier (staging preparation)

See `garden-bistro/vite-app/docs/REMAINING_WORK.md` for the full implementation and rollout plan. The copier has not been run on any live source or R2 bucket. Review and apply `migrations/002_media_PROPOSED.sql` and `005_legacy_media_map_PROPOSED.sql` only after inspecting the actual target schema and testing on an isolated copy. Set `SOURCE_DATABASE_URL` to the verified source with read-only image visibility. Run `npm run media:migrate -- --dry-run` to validate source images; dry-run does not access R2 or target. It checks the legacy schema and reports a count but does not export files.

For an approved staging copy, set server-only `DATABASE_URL` (target), the R2 credentials and public base URL listed above, `MIGRATION_UPLOADER_ID` to an existing approved Supabase Auth user UUID, and `MIGRATION_PUBLIC_MEDIA_APPROVED=yes`, then run `npm run media:migrate -- --execute`. This uploads identical source WebP bytes to the **public** R2 domain, verifies each R2 readback SHA-256 and length, and writes metadata and legacy-ID mappings in a target transaction. It does not migrate references, assign verified descriptions, verify all business records, delete source bytes or make a site ready for production. If a record or upload fails, reconcile logged object keys and target mappings before retrying. Re-running checks existing mappings against source and R2. A read-only role subject to RLS may see only part of the source: independently confirm visibility and counts before treating the result as complete. Only perform on approved images; require a tested backup and explicit owner approval before any production execution.

## Repository layout

- `garden-bistro/vite-app/`: official application, sole active package/lockfile, functions, proposed migrations, tests, assets and rollout documentation.
- `garden-bistro/legacy-next/`: archived Next.js application with its original package and migrations, retained only for data migration and rollback; its `public` symlink points to the preserved Vite public assets.
- `netlify.toml`: sole active Netlify build configuration.
- Root JPG files: original supplied photographs; preserved pending owner review.

The Vite application is **not yet ready for production**. Root Netlify config establishes the intended build target, but deployment and production cutover have not been performed or approved.

### Business profile and reference linking

The staff profile editor stores an explicitly published `businessProfile` inside existing settings and treats unknown opening hours as unspecified. The contact page displays only published, validated fields. Basic permission-scoped overview and audit views are implemented. These features have only local tests.

The reference-linking tool `npm run media:references -- --dry-run` reports unmapped, invalid and conflicting legacy image references without writing. After reviewing the actual schema, successful staging image copy, backup and change freeze, an explicitly authorized `--execute` additionally needs `MIGRATION_REFERENCES_APPROVED=yes`, `MIGRATION_ACTOR_ID`, `DATABASE_URL` and the R2 variables. It verifies R2 object bytes and adds `r2MediaId` without removing old `imageId` values. It has not been run on live data and only covers the known top-level content JSON reference; verify all other schemas and references independently. See `garden-bistro/vite-app/docs/REMAINING_WORK.md`.
